# Lessons

Entries: the pattern → what went wrong → the rule to follow.

## Verify the build environment before writing code
- **What went wrong:** Was about to scaffold a new Gradle/Java module before checking the toolchain. The machine had NO JDK (only a VASSAL-bundled JRE) — nothing could have compiled or been verified.
- **Rule:** On any build/compile task, confirm the required toolchain exists *first* (`java -version`, `JAVA_HOME`, install dirs). Surface a missing toolchain as a blocker immediately rather than producing unverifiable code. Bias toward environment/config causes on platform-specific work (per global CLAUDE.md).

## Don't use PowerShell syntax in the Bash tool
- **What went wrong:** Ran `git commit -m @'...'@` (a PowerShell here-string) inside the **Bash** tool. Bash treated `@` as a literal char, leaving a stray `@` on the commit subject and body. Fixed with `git commit --amend`.
- **Rule:** Bash tool = bash quoting (single/double quotes, `$'...'`). PowerShell tool = PowerShell syntax (`@'...'@` here-strings, `$env:`). Never mix. For multiline commit messages in bash, use multiple `-m` flags.

## winget installs aren't visible to running shells
- **What went wrong:** After `winget install` of JDK 21, the machine `JAVA_HOME`/PATH updated (registry) but the agent's spawned shells still didn't see `java`.
- **Rule:** After installing a tool mid-session, don't assume PATH updated. Read the machine env var from the registry (`[Environment]::GetEnvironmentVariable('JAVA_HOME','Machine')`), locate the install dir, and set `$env:JAVA_HOME` / prepend PATH explicitly per command until a fresh shell is available.

## Don't `pkill`/`pgrep -f` a pattern that matches your own command line
- **What went wrong:** Killed background apps with `pkill -f ControlPlaneMain` / `pgrep -f ControlPlaneMain` from a Bash command whose own command line *contained* that string. The pattern matched the running shell, killing it (exit 144) before the real work ran. Happened repeatedly in one session.
- **Rule:** Kill background jobs by exact PID (capture `$!` when launching, `kill <pid>`). If you must pattern-match, choose a pattern that cannot appear in the kill command itself (e.g. a fragment like `controlplane.Control`) and always append `| grep -v pgrep`. Never `pkill -f <X>` while `<X>` is literally in the same command.

## Shadow fat-jars break ServiceLoader-based libs (Flyway) — use `installDist`
- **What went wrong:** The `:game-control-plane` shadowJar ran but Flyway applied 0 migrations ("detected but did not follow the filename convention"). Cause: multiple jars ship `META-INF/services/org.flywaydb.core.extensibility.Plugin`; the fat jar kept only one (last-wins), so Flyway lost its SQL-migration resolver. `mergeServiceFiles()` did **not** fix it under shadow 9.4.1 (still last-wins).
- **Rule:** For apps that resolve plugins via ServiceLoader (Flyway, JDBC, SLF4J, Jetty), prefer the `application` plugin's `run`/`installDist` (each dep stays its own jar → ServiceLoader intact) over a shadow fat jar. If a fat jar is required, verify the merged `META-INF/services/*` actually contains entries from *all* contributing jars, not just one. Diagnose fat-jar-only failures by re-running on the normal classpath (`gradlew run`).

## Rebuild a bundled artifact after editing bundled resources before testing it
- **What went wrong:** Edited the Flyway migration `.sql` files (bundled into the module jar), then ran the previously-built `installDist` binary to verify the new CHECK constraints. The binary still carried the OLD migrations, so every "should-fail" insert succeeded — I nearly reported a broken schema as working.
- **Rule:** A packaged/bundled artifact (shadowJar, `installDist`, Docker image) is a *snapshot*; it does not track source like `./gradlew run` does. After changing any bundled resource, rebuild the artifact (and ideally assert the change is present in it, e.g. `unzip -p <jar> <resource> | grep ...`) before testing. When in doubt, test via `gradlew run` (live classpath) or rebuild first.

## Gradle project paths here are flat
- **What went wrong (potential):** AGENTS.md shows `./gradlew :game-app:game-core:test`, but `settings.gradle.kts` registers projects flat via `include(":game-core")` + `projectDir` override.
- **Rule:** Trust `settings.gradle.kts` for project paths: use `:game-core`, `:smoke-testing`, `:game-headless`, etc. — not `:game-app:...`.

## When integrating with a large codebase, copy its proven recipe — don't invent
- **What worked:** The headless engine-boot path was non-obvious, but `smoke-testing/GameTestUtils` already had the exact in-process recipe (GameParser.parse → assign AI players → build ServerGame with LocalNoOpMessenger + NO_OP_SENDER → runNextStep). Reusing `PointFileReaderWriter` (polygons), `GameParser` (rules), and that recipe saved re-deriving fragile setup.
- **Rule:** Before writing integration glue, find the existing seam — test utilities, `Headless*` classes, the interface the real UI implements — and copy the working recipe. The codebase usually already shows how.

## A minimal interface impl: stub only what's truly never called — run to find out
- **What went wrong:** `WebLaunchAction` blanket-threw `UnsupportedOperationException` on the LaunchAction methods I assumed were lobby-only. But `getAutoSaveFileUtils()` IS called mid-run (ServerGame writes a round-boundary autosave — separate from `setDelegateAutosavesEnabled(false)`), so the game crashed at the first round transition.
- **Rule:** Don't assume which interface methods the runtime invokes. Implement the obvious ones, then RUN it and let the stack trace reveal the rest. `setX(false)`-style flags often don't disable every related code path.

## Isolate an embedded/headless server from the user's real app settings
- **What worked:** Used `ClientSetting.setPreferences(new MemoryPreferences())` (not `ClientSetting.initialize()`, which uses the real on-disk prefs) and redirected autosaves to a temp dir. The server neither reads the user's GUI prefs nor persists changes back.
- **Rule:** When embedding an app's engine, run it on isolated/in-memory config and a throwaway working dir, so the server can't mutate or leak the user's real environment.

## Verify integration work by running the real artifact, not just unit tests
- **What worked:** Each web-port increment was proven by running it (smoke test, `runAiGame`, `runSpectator` + a live browser screenshot) — which surfaced real-world facts unit tests wouldn't: geometry-only territories (`Box1-3`, `Suiyuyan`), the autosave call path, live ownership changes. Pairs with the global "verify before complete" rule.
- **Rule:** For integration/porting, a green unit test isn't proof. Run the actual CLI/server/UI against real data and observe the output.

## Drive browser/canvas verification from the data, not from pixel-hunting
- **What went wrong:** Verifying a land move meant clicking a source territory then an adjacent enemy on a Canvas map. Guessing screen pixels for a named territory was slow and wrong — the live pan/zoom transform isn't known, so map→screen conversion drifts.
- **Rule:** For canvas-app verification, pick targets from the underlying data, not the picture. Read `geometry.json` (PowerShell `ConvertFrom-Json`) for adjacency/owners/centers to choose a valid move (e.g. "Kiangsu borders Anhwe, which is Chinese"), then use the in-app hover tooltip to confirm a tile's identity before clicking. Confirm the *outcome* from data too (hover Anhwe → "owner: Japanese").

## Re-send outstanding decision requests on (re)connect, not just latest state
- **What went wrong:** The WebSocket server's catch-up re-sent only the latest state snapshot. A browser that connected *after* a blocking decision request was broadcast never saw it, so the engine thread sat parked forever waiting for a reply.
- **Rule:** For a request/response bridge over a broadcast socket, the server must remember the outstanding request and re-send it on connect (clear it when any reply arrives). State catch-up alone strands a late/reloading client mid-decision.

## Engine `whoAmI` label must be a single colon-free token
- **What went wrong:** Constructed `WebPlayer` with label `"Human:Web"`. `ServerGame` sets `whoAmI = (isAi?"AI":"Human") + ":" + playerLabel`, and `GamePlayer.setWhoAmI` requires *exactly two* colon-separated parts — `"Human:Human:Web"` threw and killed the game on the first step.
- **Rule:** A player's label is a bare token (e.g. `"Web"`), never `"Type:Label"`. When feeding a value the engine will compose into a delimited string, don't pre-include the delimiter.

## `implementation` deps are not transitive — add the module you import directly
- **What went wrong:** `game-web-server` depends on `:game-core`, whose own deps are `implementation` (not `api`). Using `org.triplea.java.collections.IntegerMap` directly failed to compile — it lives in `:java-extras`, which `game-core` doesn't re-export.
- **Rule:** If you `import` a type, declare a direct dependency on the module that *defines* it (here `implementation(project(":java-extras"))`); don't rely on transitive visibility through `implementation` edges.

## Hit-test overlapping polygons in reverse draw order (topmost wins)
- **What went wrong:** `MapCanvas.territoryAt` returned the *first* territory whose polygon contained the click, iterating the array forward. TripleA sea-zone polygons are large and overlap coastal/island land; since sea zones come earlier in the array, a click on a visible island resolved to the sea zone *beneath* it. A diagnostic showed **29 of 90 land territories** (≈ every Pacific island) had their centroid inside a water polygon — all unclickable. This silently blocked amphibious/island movement entirely.
- **Rule:** When polygons overlap and you render in array order (later = painted on top), hit-test in **reverse** so a click resolves to what the user actually sees. "First match" is wrong for any overlapping-shape map; match the draw order. Diagnose "can't select X" UI bugs by checking polygon containment + array order against the render order, not by pixel-nudging.

## Broadcast state at the granularity the user acts, not just at phase boundaries
- **What went wrong:** the playable runner published a `StateSnapshot` only after each `runNextStep()`, but a whole move phase runs *inside* one step (the `handleMove` loop blocks the game thread), so the browser's `units` map didn't change until the phase ended — units appeared frozen while the player moved them. The engine's `UnitCollection` was correct all along; only the *projection cadence* was wrong.
- **Fix:** `WebPlayer.handleMove` now re-projects and broadcasts (`bridge.publishState(StateProjector.project(data))`) after each accepted move, via a second `Consumer<String>` (`server::publishState`) on the bridge. Map updates per-move.
- **Rule:** Push state updates at the granularity the user *acts*, not the engine's coarser loop boundaries. When a UI feed looks stale, check the publish cadence vs. the mutation cadence before suspecting the data. (Verification corollary: confirm a canvas action from the freshest authoritative feed — re-select and read the count delta — knowing which feed updates when.)

## Don't hand-wave a user's bug report — investigate the live state first
- **What went wrong:** User reported combat didn't trigger when Japanese units entered Chinese-held Kiangsi. I dismissed it twice ("Kiangsi is friendly / originally Japanese, you're mistaken") on reasoning alone. The user pushed back with the correct game logic (opposing units can't co-exist without combat) and a screenshot proving co-located Japanese + Chinese units with "No battles yet." It was a real bug.
- **Rule:** A user reporting a behavioral bug has observed something. Before concluding they're mistaken, reproduce or inspect the actual state (live snapshot, logs, the engine's own data). Their domain intuition about how the game *should* behave is evidence, not noise. Per global rule 6 (autonomous bug fixing): point at the live state, then resolve — don't argue from assumptions.

## The engine does not auto-fight battles — the seat must drive the combat phase
- **What went wrong:** `WebPlayer` handled purchase/move/place but not the battle step, assuming combat resolved itself once units were moved in. It doesn't: a `ServerGame` parks on the human seat during the combat step waiting for the player to fight each battle. With no handler, battles were silently skipped and attacker+defender sat co-located — exactly the reported bug.
- **Fix:** `handleBattle()` mirrors `AbstractAi.battle()` / `TripleAPlayer.battle()`: loop `IBattleDelegate.getBattleListing().getBattlesMap()`, call `fightBattle(where, type.isBombingRun(), type)` until none remain, ignoring `BattleDelegate.isBattleDependencyErrorMessage` (dependency-order) errors. Wired to `GameStep.isBattleStepName`.
- **Rule:** When porting a seat that implements the `Player` RPC interface, every interactive *phase* needs a handler — purchase, move, **battle**, place, etc. The combat step is interactive (casualties + retreat) and must actively call `fightBattle`; moving units in does not resolve combat. Cross-check coverage against `TripleAPlayer`/`AbstractAi` step dispatch.

## Match the test game-XML to the rulebook edition; the engine spans variants
- **What went wrong:** Built/verified 3a–3b against `ww2pac40.xml` (1st-ed "Original"), but the saved rules PDF is **2nd edition** — they differ in real combat stats (e.g. aaGun cost 6 vs 5). Cross-checking battle logic against the PDF would have surfaced phantom "bugs" that are just edition differences. Also: the 2nd-ed XML existed in the map zip but wasn't in the first extraction.
- **Rule:** A printed rulebook describes *one* ruleset; the engine is parameterized across many (multiple game XMLs + ~130 properties). Pick the target edition explicitly and point the runner/export at the matching XML. The engine XML governs behavior on any divergence; the rulebook is a cross-check, not the authority.

## Before building a subsystem, check whether the engine (and AI/Swing seats) already do it
- **What worked:** The whole "political system" (declarations of war, relationship types, mandatory US entry, mobilization bonus, China province liberation, DoW→movement gating) turned out to be **fully implemented in the unchanged engine + the Pacific game XML** — and the factory-AI seats already drive their own politics. The only gap was that the human `WebPlayer` had no handler for the politics step. So the task collapsed from "implement politics" to "surface the politics phase to the browser" (one `Player`-interface step handler + a panel). Same for the air-can't-land warning (`IMoveDelegate.getTerritoriesWhereAirCantLand` already exists; `TripleAPlayer.canAirLand` already shows the flow) and province ownership (engine liberation via `originalOwner`).
- **Rule:** For a porting/reuse project, a feature request usually maps to "wire up an existing engine capability," not "build the logic." Before designing, grep the engine for the delegate method / `Player` callback, and check what `TripleAPlayer` (Swing) and `AbstractAi` already call for that phase. Build only the missing seam.

## No engine undo for an action? Give reversibility in the UI by deferring the commit
- **What went wrong / asked:** User wanted to "undo" a declaration of war within the politics phase. But `IPoliticsDelegate` exposes only `getValidActions`/`attemptAction` — once `attemptAction` runs, the relationship change is committed and there is no reverse (matches the real game: you can't un-declare war).
- **Rule:** When the engine offers no undo for an irreversible action, don't fake a post-commit undo (that would mean re-implementing engine state reversal — off-limits when the engine is unchanged). Instead make the *UI* the reversible layer: stage the choices client-side and only call the engine on phase-end ("commit"). Re-validate each staged item at commit time and report any that a prior one superseded, rather than applying blindly.

## One shared game + broadcast socket = test/▶ manual sessions collide; isolate before E2E
- **What went wrong:** The Playwright suite kept failing its precondition (no clean politics phase) because the **single** game server has one human seat and `GameWebSocketServer` broadcasts each decision to *every* connected client — the user's open browser tab was driving the same game the headless test connected to. The client also has no WS auto-reconnect, so a server restart simply drops stale tabs.
- **Rule:** For E2E against a stateful, single-session, broadcast-to-all backend, guarantee exclusive access: restart the server fresh and ensure no other client is connected (close other tabs) before the run. Order destructive tests last and have them skip if their precondition is gone. Longer term, make the client's endpoint configurable so a test can run its own server on a separate port. (Restart churn note: `restart-web.ps1` kills the prior foreground `:game-web-server:runPlayable`, so the old background task reports exit 1 and its log monitor emits "FAILURE: Build failed" — that's the kill, not a real build failure.)

## Verify a rules claim against both the game XML and the rulebook before explaining it
- **What went wrong:** Asked whether "Unprovoked" was a real term, I first answered from a subagent's research summary and overstated the mechanics — tying the `Unprovoked` relationship label to the US mobilization trigger and getting the directionality loose. On checking the sources: `Unprovoked` *is* a real `<relationshipType>` in the map XML (set by the UK/ANZAC "declare war on Japan" action) *and* the word appears in the 2nd-ed rulebook (p.9, an unprovoked Japanese DOW on UK/ANZAC grants the US a one-time 30-IPC bonus) — but the two don't line up directionally, and the actual US-entry triggers are a separate set of condition/trigger attachments I hadn't traced.
- **Rule:** When explaining game behavior, cite the authoritative sources directly — grep the game XML for the literal term, and read the rulebook page — before asserting causation. The map author's modeling label and the rulebook's prose can share a word without sharing exact semantics. Acknowledge what you haven't traced rather than narrating a plausible mechanism.

## Self-verification is fine — but show the evidence, never a hollow "all passed" claim
- **What went wrong / clarified:** I read the user's "let's test before we commit" as "the user must hand-test every change before any commit." They corrected: self-verification *is* acceptable — what's not acceptable is reporting it as "All tests passed with no errors, implemented perfectly." That tells them nothing and earns no trust. Trust comes from the *evidence*, not the verdict.
- **Rule:** When I self-verify, present concrete proof in the report: the actual observed values (e.g. the full stat table and how it matched the reference), what I clicked and what happened, exact outcomes, screenshots, real numbers — enough that the user could audit the claim. Never substitute a vague success assertion ("works perfectly", "all green") for the substance. State what I checked, what I *didn't*, and anything uncertain. Then a normal commit is fine without a mandatory hand-off — the evidence is the gate, not a ceremony. (They can still ask to drive a hands-on test; honor that when asked.)

## Read map resources directly from the file path, not via ResourceLoader, when headless
- **What worked:** Two info tabs needed map data — game **notes** and **objectives.properties**. The engine's normal path (`ResourceLoader.loadPropertyFile`, `GameNotes.loadGameNotes`) is built for the headed game: ResourceLoader needs asset paths we deliberately skip (`setSkipMapResourceLoading(true)`), and `GameNotes.loadGameNotes` *migrate-writes* a `.notes.html` file as a side effect. Cheaper + side-effect-free: (a) notes are a `<property name="notes">`, so the parser already exposes them — `gameData.getProperties().get("notes", "")` returns the HTML, no map-data dep, no file write; (b) objectives.properties lives at the map root, so load it with plain `Properties.load` from `gameXml.getParent().getParent().resolve("objectives.properties")`.
- **Rule:** When porting a feature that reads map files headless, first check whether the parsed `GameData` already carries the value (game properties), then fall back to reading the file directly from a path derived from the game XML. Avoid ResourceLoader (asset-path setup we skip) and any "load" helper that writes/migrates files. (Map resource files like objectives.properties aren't extracted by default — pull them from the map zip like the 2nd-ed XML.)

## Evaluate engine conditions read-only by copying the panel's dummy-bridge recipe
- **What worked:** The Objectives tab needed to test rules/trigger conditions (`RulesAttachment.isSatisfied`), which can *mutate* state (chance decrement, random rolls). The Swing `ObjectivePanel` already solved this: evaluate via `AbstractConditionsAttachment.testAllConditionsRecursive(getAllConditionsRecursive(conds, null), null, new ObjectiveDummyDelegateBridge(data))`. The dummy bridge makes it safe — `addChange` is a no-op and `getRandom` returns 0 — so testing can't corrupt the game. Reused it verbatim; results exact-matched the base game.
- **Rule:** Before evaluating engine conditions/triggers yourself, find the read-only harness the engine already uses (here `ObjectiveDummyDelegateBridge`) and reuse it. Don't call `isSatisfied`/delegate logic with a live bridge — it can write history, roll dice, or decrement chance. Run such evaluation on the game-loop thread (no read lock needed there, unlike the Swing EDT path).

## Reimplement only the few engine computations that need UI-layer inputs (MapData)
- **What worked:** The Players/Resources stats wanted the engine's `IStat` classes, but `TuvStat`/`UnitsStat` call `mapData.shouldDrawUnit(...)` and we have no `MapData` headless. Rather than fake a MapData, I reimplemented those ~5 formulas directly (count all units; TUV via `TuvCostsCalculator`, which needs no MapData; production via `TerritoryAttachment.getProduction` × `getPuMultiplier`). On Pacific the totals exact-matched the base StatPanel/EconomyPanel.
- **Rule:** When reusing an engine computation that drags in a UI-layer dependency (MapData, ResourceLoader, images), check whether that dependency actually changes the result for your case. If it's only a display filter (shouldDrawUnit), reimplement the handful of formulas without it and verify the numbers match the base game, rather than constructing the heavy UI object headless.

## Auto-focusing UI on incoming events fights the user navigating
- **What went wrong (UX):** The dock auto-switches to the "Actions" tab whenever a new decision request arrives — sensible to surface a decision, but it repeatedly yanked me off the Players/Objectives/Relationships tab mid-look during testing (every page reload re-fires the politics request). It's intended behavior but actively annoying when browsing info.
- **Rule:** "Grab focus on a new event" and "let the user browse" conflict. Gate auto-focus on whether the user has *manually* navigated away (e.g. only auto-switch if they're still on the default/Actions tab, or use a subtler cue like the existing ● badge). Flag this class of interruption when you notice yourself fighting it during verification.

## A mid-decision sub-query rides the existing request/await loop as a re-prompt — don't add a channel
- **What worked:** Live move-route *preview* needed a client→server round-trip *during* a pending move decision. The `WebDecisionBridge` is strictly `requestId`-keyed request/reply (engine parks on `await`, WS thread completes the matching future) — there's **no out-of-band query channel**, and adding one would mean the WS thread handling unsolicited client messages + a way to respond without ending the decision. Instead, the preview is just another *reply kind*: the client replies `{previewRoute:{…}}`, the server computes the route and `continue`s the loop to re-`await("move", …)` with the result attached as `MoveRequest.preview` — exactly how the `error` field already re-prompts after a rejected move. The client keeps its local selection across the re-prompt; the new request (new id) just carries the computed route to highlight.
- **Rule:** When you need an interim computation mid-decision over a request/reply bridge, model it as an additional **reply kind that re-prompts the same request** (carrying the result in the next request payload), not a new socket/message channel. Mirror an existing re-prompt path (here `error`) so the parking/loop semantics stay identical. The bridge being requestId-keyed is the constraint that makes the re-prompt the clean fit — and keeps the engine the single driver.

## Carried/dependent units don't move under their own power — exempt them from movement checks
- **What went wrong:** The move preview flagged transported infantry/artillery as "can't reach" (user-reported). The reachability check compared each unit's *own* `getMovementLeft()` (0 for cargo aboard a transport) to the route cost — but cargo **rides with its transport**; its own movement is irrelevant to whether the transport's move reaches the destination. The same applies to any dependent unit (carrier-based air, etc.).
- **Rule:** When computing per-unit movement/reachability, exempt units that move as a *dependent* of another unit (`Matches.unitIsBeingTransported()`, carried aircraft). Use the same predicate the code already uses to *surface* those units (here `movableMatch`'s `unitIsBeingTransported` cargo branch) so "shown as movable" and "counted as able to reach" stay consistent. A 0-movement unit isn't necessarily stuck — check why it's 0 (spent vs. carried) before treating it as blocked.

## On this Linux VM, SDKMAN (Java) and nvm (Node) aren't auto-sourced in tool shells
- **What went wrong:** Non-interactive Bash-tool shells don't run the interactive profile that sources SDKMAN/nvm, so `java`/`node` were missing even though both are installed — `:game-web-server` tasks and `npm` fail until the managers are sourced. (Mirrors the Windows winget/PATH lesson: a per-user version manager isn't visible to a fresh non-interactive shell.)
- **Rule:** On this machine, prefix any JVM/Node command with the sourcing: `source "$HOME/.sdkman/bin/sdkman-init.sh"` + `export JAVA_HOME="$HOME/.sdkman/candidates/java/current"` for Gradle/Java, and `source "$HOME/.nvm/nvm.sh" && nvm use 22` for npm/node. State doesn't persist between Bash-tool calls, so re-source per command. (See the `linux-dev-environment` memory.)

## Don't pipe a command through `tail` when you care about its exit status
- **What went wrong:** Ran `./gradlew … 2>&1 | tail -40` in the background; the task notification reported "exit code 0" but Gradle had actually `BUILD FAILED` — `tail` exits 0 and masks the upstream exit code, so the real failure was hidden.
- **Rule:** When the exit code matters (builds, tests, anything gated on success), don't end the pipeline with `tail`/`head`/`grep` and read the pipeline's status as the command's. Use `set -o pipefail`, capture `${PIPESTATUS[0]}`, or run the command unpiped and slice the output separately. A green exit from a filtered pipe is not a green build.

## When a design decision rests on an external artifact, read the artifact — don't infer it from a proxy
- **What went wrong (caught, not shipped):** I characterized the legacy TripleA lobby schema from its *client DTOs* in-repo and nearly let the Phase 4 reuse plan rest on that inference. Reading the actual upstream `spitfire-server` SQL changed the conclusion materially: their game model is an ephemeral P2P *advertisement* with no game-state/seats/resume (so it can't seed our resumable-game tables at all), and the whole lobby module was *deleted upstream mid-2024* (so "adopt their migrations" meant adopting an abandoned subsystem). The DTOs implied a richer reuse than the schema actually offered.
- **Rule:** Before a recommendation depends on an external system's design (a schema, an API, a config), go read the authoritative artifact, not a proxy for it (client stubs, docs, your memory of it). Proxies omit exactly the structural facts (here: persistence model, lifecycle, maintenance status) that decide reuse-vs-greenfield. Delegate the fetch to a subagent if it's large, but ground the call in the real thing.

## Exclude the engine's "optional" players from human seat selection
- **What happened:** The web-port seat-select screen listed all 8 Pacific nations, including the passive minors (Russians/French/Dutch). The user noted these are inert factions that shouldn't clutter the picker.
- **Rule:** When surfacing nations as human-claimable seats, exclude players flagged `GamePlayer.getOptional()` — the engine's "optional"/passive minors (the same flag `StateProjector`'s `passive` uses, which the Players tab collapses into "Other"). Crucial distinction: the engine still needs a `Player` for *every* nation, so filter the optional ones out of the **roster** (what the human picks from), NOT out of the player set — `buildPlayers` still creates an inert AI for them. "Show only what a person would actually play" ≠ "only build players for those."

## Match the reconnection strategy to the sync model (snapshot vs incremental events)
- **What happened:** The Phase 4 spec called for Lichess-style **versioned events + `lastSeenVersion` replay** for reconnection. On building it, that's a pattern for systems that stream *incremental* events — but the web port broadcasts **full state snapshots**, so `onOpen` re-sending the latest snapshot already catches a reconnecting client up completely. The only real gap was *transient* events not in the snapshot (the battle log), fixed with a small bounded cache replayed on connect. Versioned-event machinery was unnecessary.
- **Rule:** Before importing a reconnection pattern, identify your sync model. **Snapshot-broadcast** → reconnection = re-send the latest snapshot + replay any *transient* side-events (battle log, toasts) you don't fold into the snapshot. **Incremental-event** → you need versioning/`lastSeenVersion`/ack. Don't bolt event-versioning onto a snapshot system; it's complexity with no payoff. (Recorded in `PHASE-4-MULTIPLAYER.md` §6.2.)

## Reconnect must re-bind the seat AND confirm a live takeover — don't silently claim or strand a decision
- **What went wrong (user-reported):** After multiplayer seat routing, closing the browser and reopening left the player unable to act mid-game. The reopened page reconnected as an **unbound spectator** — the seat was remembered in `sessionStorage`, which is **cleared on a full browser close** — so the seat's *buffered decision* (the engine parked in `await`) was never delivered: no panel, can't select anything. The user also (rightly) asked whether silently auto-claiming on reconnect was safe — it isn't: latest-claim-wins would **evict** whoever holds the seat, or grab a **stale** seat from a previous game.
- **Rule:** For a stateful, seat-routed session, reconnection has three obligations: **(1) re-bind** — the client must re-claim its seat or it receives no routed messages (and the server should replay the seat's outstanding request on bind, which ours does); **(2) persist at the right scope** — `sessionStorage` is per-tab and dies on browser close, so use it as primary (keeps two tabs distinct, survives a tab reload) with `localStorage` as the cross-close fallback; **(3) confirm a *running*-game takeover** — show "Rejoin?"/"Take over from {name}?" rather than silently claiming, and only offer seats that are actually reclaimable (mark human-driven seats server-side so you don't offer dead AI seats). Auto-reclaim is fine only in a pre-game/setup phase where claiming is harmless.

## "Unexpected behavior" can be standard engine/data behavior surfaced differently — check before assuming a code bug
- **What happened (user-reported):** A new Pacific game looked like it "let the AI act before Japan's turn 1." It wasn't a web-port bug: the game XML `<sequence>` runs game-init plus a `bid`/`placeBid` step for *every* power before the first real turn. Bidding is an A&A tournament balancing house-rule that's **off by default** (all `<power> bid` properties = 0), so those steps are no-ops — but our game loop published a full state snapshot after every `runNextStep()`, so the client flashed through "Americans Bid", "Chinese Bid", … The engine was doing exactly what the map defined; our **per-step publish** made an invisible-on-desktop formality visible.
- **Rule:** When a report says "X happens that shouldn't," first ask whether X is the engine's/data's *standard* behavior surfaced by a difference in *our* layer (rendering, publish cadence, logging), not new logic we wrote. Read the authoritative artifact (here the `<sequence>`/`<delegate>`/`<property>` in the map XML) before theorizing about our code. The fix usually belongs in the presentation layer (suppress/transform the surfaced no-op), not in re-implementing engine logic — and should be **conditioned on the real predicate** (we gated the skip on `BidPurchaseDelegate.doesPlayerHaveBid`, so a non-zero bid still shows) rather than a blanket suppression that would hide the behavior when it *does* matter.

## Rebuild the runnable artifact, not just `:test`, before running an integration stack — and verify the build actually ran
- **What went wrong (cost ~an hour of M6 verification):** I changed control-plane code, ran `:game-control-plane:test` (passed), then started the control plane from `build/install/.../bin` and saw the OLD behavior (`/connect` returned the pre-change shape). `:test` compiles `build/classes` but does **not** refresh the `installDist` jar; the launcher runs the stale jar. Worse, a wrapper script's `./gradlew installDist` step silently did nothing on one run (empty log, stale jar) — I trusted "the script ran" instead of checking the artifact.
- **Rule:** When an integration test runs a *packaged* artifact (installDist/shadow/Docker image), the rebuild chain is `compile → jar → installDist → (docker build)`. Running `:test` proves the code compiles, not that the artifact is current. After building, **verify the artifact**: check the jar's mtime, or `unzip -p <jar> <Class>.class | strings | grep <new-symbol>`, or grep the running process's classpath. For Docker, rebuild the image too (a running container keeps old code; only NEW containers pick up the rebuild). Don't infer "rebuilt" from "the build command was in my script."

## Javalin (and most routers): a literal path segment can be shadowed by a sibling path-param route — use a non-colliding path
- **What went wrong:** `GET /api/games/mine` was being handled by `GET /api/games/{id}` (it parsed `id="mine"` → "No such table"), even though I registered the literal route first. Registration order didn't save it.
- **Rule:** Don't put a fixed sub-resource at the same depth as a path param on the same parent (`/games/mine` vs `/games/{id}`) and assume specificity wins — behavior is router/version-dependent. Use a distinct path (`/api/my-games`) or a clearly-separated namespace. Cheap to verify: `curl` the literal path and confirm it hits the intended handler, not the param route's error.

## A WebSocket client that attaches its `open` listener *after* construction can miss the event — send in the handler, or latch the state
- **What went wrong:** My test client created `new WS(url)` and only attached the `open` listener later (inside an `onOpen()` await helper). For a fast/local connection the socket opened *before* the listener was attached, so the promise never resolved — and because an unsettled promise doesn't keep Node's event loop alive, the process exited 0 with output silently truncated (looked like "passed but stopped early").
- **Rule:** With `ws`/browser WebSocket, either send your first message inside the `ws.on("open"|onopen)` handler (attached synchronously at construction), or latch `opened`/`closed` flags in listeners attached immediately and have your await-helper resolve if already-open/closed. Never rely on attaching `open` "later." And when a Node script "exits 0 but stops mid-way," suspect an unresolved promise (a missed event) before suspecting the logic.

## A freshly-spawned server may accept TCP before its message path is stable — gate integration tests on a real round-trip, not a bare connect
- **What happened (M6 verification):** The lazy-spawned game container's `waitForReady` returns once the TCP port accepts, but the WS server's *inbound* path isn't immediately stable — the first connection(s) had their first message silently dropped (no handler call, and the connection went half-dead so the auth-timeout's `conn.isOpen()` read false and never closed it). A bare "did the socket open?" warm-up passed while the real auth message vanished. Gating warm-up on a full round-trip (send a bogus auth, wait until the container actually *rejects* it) made the suite reliable.
- **Rule:** "Port accepts a connection" ≠ "server is ready to process messages." For integration tests against a just-started service, warm up with an operation that exercises the real request→response path and wait for the response, not just for connect. Note the same gap for production (here: filed a follow-up for a WS ping/pong heartbeat + readiness handshake, since `waitForReady` only probes TCP and a half-dead first connection isn't caught by an app-level timeout).
